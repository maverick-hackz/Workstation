# SBOM & Sigstore

> Software-Bill-of-Materials standards (SPDX, CycloneDX) + signing/transparency (Sigstore: cosign, Fulcio, Rekor). Defensive primitives, but understanding them helps red teams find the gaps.

## TL;DR
- **SBOM** is a structured list of every component (incl. version, supplier, optionally hash + license) that goes into a build. Two leading formats: **SPDX** (ISO/IEC 5962) and **CycloneDX** (OWASP).
- **Sigstore** = keyless signing for software artefacts. **cosign** signs (image, blob, OCI), **Fulcio** issues short-lived certificates bound to OIDC identity, **Rekor** is the transparency log.
- Generate SBOM with **Syft** (Anchore); sign image + SBOM with **cosign**; verify at admission with **Kyverno** / **Sigstore policy-controller**.
- Regulatory drivers: US EO 14028 (federal procurement requires SBOM), EU CRA (mandatory vulnerability handling for products entering the EU market by Dec 2027).

## SBOM formats

### SPDX (ISO/IEC 5962:2021)
- Tag-value, JSON, YAML, or RDF. SBOM ID (`SPDXID`), document namespace, packages, files, relationships.
- Best for legal/license workflows; strong on supplier identity.
- Generate: `syft <image> -o spdx-json=sbom.spdx.json`

### CycloneDX (OWASP)
- JSON or XML, BOM-Link references, vulnerability-centric metadata, sub-flavours for VEX (Vulnerability Exploitability eXchange) and CBOM (cryptographic).
- Best for vuln workflows; tighter integration with scanners (Trivy/Grype consume natively).
- Generate: `syft <image> -o cyclonedx-json=sbom.cdx.json`

### VEX (within CycloneDX)
Describes whether a vulnerability *actually affects* the product (status: `not_affected`, `affected`, `fixed`, `under_investigation`) with an `impactStatement`. Distinguishes "CVE-X is in our SBOM but our config doesn't reach it" from "we're vulnerable, patch incoming". Consumer can filter scanner output by VEX status.

## Sigstore primitives

### cosign — sign & verify
```bash
# Keyless signing (Fulcio issues a short-lived cert bound to your OIDC identity)
cosign sign registry.acme.tld/app@sha256:abc...

# Or with a long-lived key
cosign generate-key-pair                 # creates cosign.key + cosign.pub
cosign sign --key cosign.key registry.acme.tld/app@sha256:abc...

# Verify
cosign verify --certificate-identity 'github-actions@acme.tld' \
              --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
              registry.acme.tld/app@sha256:abc...

# Attach an SBOM as an attestation (in-toto format)
cosign attest --predicate sbom.cdx.json --type cyclonedx \
              registry.acme.tld/app@sha256:abc...

# Verify the SBOM attestation
cosign verify-attestation --type cyclonedx \
                          --certificate-identity 'github-actions@acme.tld' \
                          --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
                          registry.acme.tld/app@sha256:abc... \
  | jq -r '.payload' | base64 -d | jq
```

### Fulcio (CA)
Issues a short-lived (10-minute) X.509 cert with the subject set to the OIDC identity (GitHub Actions OIDC, GitLab CI OIDC, Google / Microsoft / Sigstore identity providers). The cert chains to the Sigstore root, which is the trust anchor for verifiers.

### Rekor (transparency log)
Every cosign signature is published to a Merkle-tree append-only log (`rekor.sigstore.dev`). Verifiers can require that the inclusion proof matches, ensuring the signature was published before a known good time (`--sct` / `--rekor-url`).

## Detection / Discovery — what red team looks for

| Finding | Why it matters |
| --- | --- |
| Repo ships releases without SBOM | Unknown ingredient list = unscanned attack surface. |
| Repo signs releases with a long-lived dev key, key on disk | One developer compromise = supply-chain compromise. Prefer keyless. |
| SBOM exists but is generated post-release on the artifact, not at build | SBOM may not match what was actually built; "build-and-scan" parity issue. |
| Image signature verified at deploy with `--certificate-identity *` (wildcard) | Anyone with a Fulcio cert can sign; defeats the purpose. Pin the identity. |
| Image signed but Rekor inclusion proof not required | Replay/log-tampering window. |
| No VEX attestation | Scanner alerts on CVEs that don't actually apply; alert fatigue → bypass. |

## Exploitation paths defenders need to know
- **Build-time injection** ([./poisoned-pipeline-execution.md](./poisoned-pipeline-execution.md)) → SBOM generated by the same poisoned pipeline matches the malicious artefact (SBOM-as-truth fallacy). Mitigation: SBOM generation from an isolated stage or from a third party.
- **Signature verification skip** in production deploy because the local Sigstore root was out of date — verifier soft-fails. Fail-closed verifier required.
- **SBOM tampering** if the SBOM is not signed itself. Always attest it (`cosign attest`), don't just attach as a layer.
- **Internal proxy registry that strips signatures** — pulling from `internal.registry/acme/app` returns the layers but not the signature object. Verify against the original registry or copy signatures via `cosign copy`.

## Defence / Remediation
- **Generate SBOM at build, sign it, store it alongside the artefact**. Syft + cosign attest is the canonical OSS pipeline. The SBOM is the ship artefact.
- **Pin verification identity** when verifying signatures:
  ```bash
  cosign verify \
    --certificate-identity 'https://github.com/acme/app/.github/workflows/release.yml@refs/heads/main' \
    --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
    registry.acme.tld/app@sha256:...
  ```
- **Require Rekor inclusion proof** (`--rekor-url` defaults to Sigstore public; for self-hosted, pin to your Rekor).
- **Admission control at deploy** — Kyverno / Sigstore policy-controller verifies signature + attestation before pod admission.
- **VEX feedback loop** — scanner output filtered through VEX so dev tickets reflect real risk; SLAs measured against `affected` only.
- **Self-host the trust anchor** for high-assurance environments (private Fulcio + private Rekor); public Sigstore is fine for most use cases.
- **Reproducible builds** (deterministic compile flags, build envelope captured in a SLSA provenance attestation) — verifier can rebuild and compare against the signed artefact.
- **SLSA framework levels 1-3** as posture targets; level 3 requires provenance attested by an isolated builder. https://slsa.dev/spec/v1.0/levels
